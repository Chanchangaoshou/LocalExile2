## 问题 1（主阻断）：世界从不被 tick，0x2f7 进了队列却永不派发

**现象（已实证，Frida v5/v6 多次会话）**：登录、选人、实例连接、区域生成全部正常；
客户端回 C→S `0x9a` 后，网关 6 ms 内发出世界组 `0x2f7` CreateObject（玩家）；
客户端世界工厂 `0x142186c20` **确实创建了该消息对象**（created=1），但此后：

- 世界分发器 `0x1421343c0` 调用 **0 次**
- 世界激活 `0x14212fd90` 调用 **0 次**
- 队列排空 `0x142130360` 调用 **0 次**
- 实体构造器 `0x141e705d0` 调用 **0 次**
- 类型登记从未以 `0xa7000ea0` 被查询

客户端停在加载界面，无报错、无断线，直到用户退出（最长观察 2.5 分钟）。

**已实证的机理**：

- 一切世界派发都过总闸 `[world+0x84a]`，全二进制仅 4 个写点：激活内 2 处、
  世界更新 `0x142130840`（虚表 +0x448）内 2 处。泵没有绕闸的即时派发分支。
- 世界更新入口无条件抬闸并派发 stamp=0 的消息——我们的 `0x2f7` 正是 stamp=0。
  由「派发 0 次」反推：**世界更新在实例会话期间从未运行**。
- 激活回调 `0x1416820a0` 本身无条件（首指令即调激活），门在虚表槽的调用方层。
- 世界聚合对象已被实例创建链构造、存在于 `session+0x20f0`，不是没建。
- **登录/选角阶段的世界更新跑过 7 次**（菜单背景世界被正常 tick），实例会话开始后归零。

**已被证伪/排除的方向（不要重复劳动）**：

- ❌ stamp 取值：世界 stamp 三件套 ctor 初值就是 0，唯一推进者是 area-object 驱动的
  `0x142137270`；服务器填 0 与初值一致。不要改 stamp。
- ❌ 实例 `0x21`/`0x22` 状态同步：与世界/激活无任何数据流关联，不要为了激活发它们。
- ❌ 「InstMgr tick `0x14218bf90` 驱动世界更新」：v6 探针实证该函数整场会话从未被调用
  （同一批钩子里的 world_update 钩子有触发，钩子有效）。真正的 +0x448 调用方另有其人。
- ❌ 类型哈希错误：工厂已建出对象且无「Unknown object type」抛错；该错误只会在派发时
  查登记才可能出现，而派发根本没发生。
- ❌ 加密/格式问题：`0x2f7` 在客户端被逐字节正确解密（探针实录）。

**当前主假设（推断，证据链完整但注册点未定位）**：实例世界没有被登记进驱动更新的
那份 tick 名单（或加载态下状态机没把 tick 交给它）；真实服务器与我们的差异最可能在
进图前后的**完整实例消息序列**——某个游戏状态监听者（分发器 default forwarder
`0x142125628` 按 `[msg+0x10]` 分发给 `[session+0x48]` / `[session+0x20]` /
`[session+0x23e8]` 三组）要先收到某些实例消息才完成登记/切态。
候选消息：实例 `0x23`（内容设置，read `0x1421582b0`，上轮只读到中段）、`0x28`
（handler `0x14212227f`）、`0x29`（实例转移类），或某个 default 转发 id。

**后续思路（按序）**：

1. 静态续查（进行中）：tick 名单的注册点（对名单向量的 append 调用方）；三组监听者的
   注册点与各自关心的消息 id；`0x23` read 后半段与 `0x28` 的完整线格式。
2. 探针加强：对 tick 名单向量下写监视（Frida MemoryAccessMonitor），一次会话抓到
   「谁在何时把哪个世界登记进去」——重点对比菜单世界登记与实例世界的差异。
3. 服务端实验（格式定死之后，一条一条试、探针全程记录）：在 `0x1e` 后/`0x9a` 前后
   补发 `0x23` 最小形 → 无效再试 `0x28` 最小形 → 再 `0x29`。每试一条看
   world_update / world_dispatch 计数是否从 0 变成非 0。
4. 若以上仍不通：**全链从头审计**（用户 2026-11-04 明确要求）：枚举真实服务器在
   登录→进图全程应发的每一条实例消息（以 0.5.5 双工厂目录 + 全部专用 handler 为
   清单），与我们实际发出的逐条 diff，连 `0x1e` 的每个字段取值一起复核，
   列全差异再逐个补，不再逐点试探。

## 问题 2：选角界面职业永远显示第 0 行（野蛮人）

**现象（用户多次实测）**：任何角色在选角界面都显示野蛮人（Characters 表第 0 行）。
角色实际职业存的是 PoE2 编号（女巫=1，DB 与网关日志可证）。

**已实证**：繁中 Characters 表第 0 行=野蠻人、第 1 行=女巫（GGPK 原表）；
真机抓包解密证实 Auth 发出的 `0x15` 里 fork 认定的职业字段=1、没发错；
`0x15` 条目读函数 `0x142716700` 消费的字节数与 fork 写出一致（不断流）。

**已证伪**：把职业号镜像写入条目 +0x40 的 u32（提交 `5c87704`）——用户实测仍显示
野蛮人，该推断作废，不要再试同类镜像。

**后续思路（从零重查，进行中）**：

1. 独立重导两边映射并逐项 diff：从读函数逐指令导出「线字段→条目对象偏移」全表，
   再对照 fork 的 CharacterEntries 写出代码——包括复核「读函数已验证」这个旧结论
   本身是否出错（字段消费一致 ≠ 语义对应一致）。
2. 顺选角 UI 的渲染路径定位职业来源：找 Characters 表的基址全局与行访问函数，
   筛它的调用方中与角色列表相关的，确定 UI 到底读条目的哪个偏移当行号；
   若行号不来自条目，找出真正的来源（另一张表按条目某键查、或条目之外的报文）。
3. 顺带核查 C→S `0x12` 创角的职业字段与 fork 读取是否一致（创角存档是否正确）。

结论将写入本目录 `CLASS-DISPLAY-NOTES.md`（尚未产出）。

## 问题 3：网关物品层数据表仍是旧代导出

**现状（已实证）**：网关的 SkillGems/物品相关表是旧一代客户端的导出。已出过一次事故：
女巫 StartSkillGem 指向第 3951 行、旧表行数不足，出生装备生成时越界崩溃、连接断在
区域包发出之前（提交 `4f5d945` 已加边界防护，越界=空出生装，不再崩）。

**后续思路**：用仓库的 GGPK 提取工具从 0.5.5 `Content.ggpk` 整表重导出
（BaseItemTypes 已有纯 0.5.5 版用于命令台；网关侧 SkillGems/Characters/StartKit
相关表逐张替换并跑回归）。人物能进图后再做，避免与问题 1 互相干扰。

## 问题 4：0x1e 里两块格式未逆出（升华/地形）

**现状（已实证）**：`0x1e` 的 LeagueStats 对表（flags0&0x80，元素构造 `0x1423bacb0`）
与地形块（flags1&0x04，`0x14212aa70`）的 0.5.5 编码未逆出；`AreaInstance.Encode`
遇非空 LeagueStats 或 TerrainData 直接抛 NotSupportedException（不发猜测格式）。
新角色进普通区域两者皆空，不受影响；**升华职业与 Delve 区域被此卡住**。

**后续思路**：人物进图后，按 read 函数 `0x14211d340` 对应分支逐指令逆这两块的线
格式，或用探针在真实流程（官方服不可得，只能靠静态+构造验证）外的方式定版。

## 问题 5：已部署但未获用户确认的修复（2 项）

1. **删角确认长度**（提交 `1e3ca9d`）：S→C `0x0d` 等六个 id 的消息实为 u16+u32
   共 8 字节（共用 vtable `0x143509F18`、read `0x14214e460`），fork 已按此改型。
   此前旧 4 字节版造成删角后接收流错位级联断线。下次删角时顺带验证，不要单独宣布修好。
2. **Play 的 Index 语义存疑（待验假设）**：2026-11-04 12:27 观察到用户选了第 3 个
   角色（`0x10` B=3），随后 Play（`0x0e`）带 Index=0x1，Auth 按 1-based 解析发了
   条目 0 的票。若客户端的 Play 指「刚选中的那个」，解析就是错的。待进图链路通后
   用多角色实测判定。

## 问题 6：Gateway.Tests 有 386 个既有失败（数据环境，非协议）

**已实证**：在父提交 `5e1c783` 的干净 worktree 上同类测试同样全灭，根因是 PC 检出
的游戏数据目录缺 `Program.Stats` 期望的键，与历次协议改动无关。Core（423/423）与
Data（34/34）全绿。**后续**：若要清，先对齐 PC 的数据目录导出，再谈测试，不要在
协议工作里顺手改测试环境。

## 问题 7：运维脆弱点——PC 重启后全栈死亡

**已实证（2026-11-04 10:55 事故）**：五件套（补丁桩 13060 / HTTPS 443 / Auth 21260 /
Gateway 6112 / 命令桥 7010）无一自启，PC 重启全部死亡，且 hosts 四条重定向
（三个补丁域名 + 登录域名 `local.pathofexile.com`）会丢失；曾因此让客户端连上真实
补丁服下载官方 exe（幸未落地）。**排障铁律**：重启后先查「五端口 + hosts 四条 +
代理绕过（NO_PROXY/WinHTTP）」全套，再谈测试。**后续**：可做一个开机自启的
看门狗脚本（WMI/计划任务），优先级低于进图。
